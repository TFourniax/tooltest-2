## Implemented boundary and review

The existing admitted working-tree reader supplies source bytes. One subprocess
per task-context request sends Python sources to the configured Core executable;
there is no shell, network call, provider-driven path read or persisted source.
The consumer checks exact ordered paths/hashes, schema and provider, module name,
fact fields/authority, line bounds and recomputed coverage. Strict UTF-8 and a
lossless JSON roundtrip reject malformed encoding and duplicate object fields.
Limits are 64 files, 128 KiB per file, 640 KiB aggregate source, 2 MiB response
and a 500 ms subprocess deadline. These are admission bounds, not a claim that
every bounded input completes within the unchanged product latency budgets.

Task symbols/imports use Python AST results when available. Invalid Python stays
unparsed with empty symbols/imports. Missing/old Core, invalid responses and
timeouts retain the existing heuristic fallback with explicit structureCoverage;
no native required-assurance rule changes. Cache keys include actual source bytes
and provider result/coverage; cached results remain detached from callers.
Other language heuristics, route/table/technology inference, and feature-map
extraction remain separate existing consumers awaiting adoption. This is not
complete PM-004 coverage or a runtime call graph.

Implementing-agent review found that reading the legacy integration configuration
also migrated/deleted it. A new regression failed before adding a read-only
option to the existing configuration reader. The default migration behavior of
other callers is unchanged; this advisory path explicitly disables migration.
Review is MACHINE, not independent review or HUMAN PASS.
